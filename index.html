01

Why we started

The problem the project set out to solve.

why we started · the bottleneck

Code review does not scale with the team

Every merge request needs a human with time, context and consistency. That combination is the scarcest resource on an engineering team.

latency

Merge requests sit idle

Work is finished but waits for a reviewer to become free.

bottleneck

Seniors read diffs

The most experienced engineers spend hours reviewing instead of building.

consistency

Every reviewer differs

The bar for good enough moves depending on who is looking.

repetition

The same comments

Identical style and validation notes get typed out, merge request after merge request.

risk

Issues reach main

Tired eyes miss what a systematic check would catch every time.

security

Vulnerabilities slip

Injection risks and unsafe patterns pass under deadline pressure.

why we started · our solution

We chose Kodus to fix it

Kodus is an open-source AI code review platform. Its agent, Kody, reads every merge request and comments on bugs, security, performance and architecture — automatically, on every merge request, so the bottleneck from the previous slide stops being a person.

what it is

A first pass, not a verdict

Kody comments on every merge request the moment it opens. A human still reviews and still decides whether to merge — the goal is to remove the repetitive work, not the judgement.

what it is

Context aware

A hybrid pipeline parses the code structure first, then gives the model precise context — fewer hallucinations than sending a raw diff.

why this one

Self-hostable

Runs entirely on our own infrastructure. Source code never leaves Felcloud and is never used to train a third-party model.

why this one

Bring your own model

Any OpenAI-compatible endpoint works, which left the choice of model and its cost entirely in our hands.

what we deployed · the model

Two models, two different trade-offs

Kodus is model-agnostic by design, so we tested more than one endpoint and found neither is a clean win on every axis.

poolside/laguna-xs-2.1 · nvidia build

Best review quality we saw

Caught a hardcoded authentication bypass and a prompt-injection risk on real merge requests, with full attack-path explanations.

Trade-off: it's a cloud endpoint, so code leaves Felcloud infrastructure to reach it, and it hit a request-budget limit (44/32) on very large PRs.

qwen2.5-coder:3b · self-hosted

Runs on our own infrastructure

A coding-specialised model served from Felcloud, behind an OpenAI-compatible endpoint. No quota, no per-token cost.

Trade-off: review quality on the endpoint we tested was noticeably behind poolside's on the same merge requests.

where this leaves us

The cloud model achieved the strongest review performance, but Qwen was still a solid in-house alternative. The trade-off is mainly between maximum review quality and keeping code and analysis fully within our infrastructure.

what we deployed · security

The VM was wide open, then it wasn't

An audit of the deployment found every service, including both databases, listening on the public interface. Anything that could route to the machine could reach Postgres and MongoDB directly.

before

Eight ports on 0.0.0.0

Web UI, API, webhooks, MCP manager, Postgres, MongoDB and RabbitMQ all bound to every interface. Postgres and MongoDB sat on random ports Docker reassigned on every restart.

The dashboard also only resolved through an SSH tunnel to localhost:3000, unusable from a normal browser.

after

One way in, through nginx

Every container rebound to loopback. Nginx is now the only public entry point, and it proxies the web UI, API and webhook ports the GitLab integration needs.

The dashboard resolves at the machine's real address, no tunnel required.

why this matters

This closed the gap between "source code stays on Felcloud infrastructure" and reality: until this fix, the databases holding that code and its review history were reachable by anyone who could route to the VM.

03

From manual to one click

The part of the work that changed the most over two months.

from manual to one click · the progression

The same deployment, three times over

Each stage removed a category of human error, and each one was only possible because we had already done the stage before it.

STAGE 01

By hand

SSH to the machine, clone the installer, generate secrets, run the install script, start the remaining containers.

It worked, and it taught us what the system actually needs. It was also unrepeatable: every step was a chance to do something slightly differently.

Anyone redeploying had to read our notes
STAGE 02

An Ansible role

Everything above written down as code: prerequisites, container runtime, secrets handling, configuration and health checks.

Idempotent, so running it twice changes nothing the second time. Secrets encrypted in a vault rather than pasted into a terminal.

Anyone with the vault password could redeploy
STAGE 03

Semaphore UI

A web interface that clones the repository, runs the playbook and streams the output to a browser.

Credentials live in an encrypted store, so running a deployment no longer requires holding the SSH key or the vault password at all.

Anyone on the team can redeploy, from a browser

from manual to one click · the role

Two modes, one playbook

fresh mode

Build from an empty machine

Installs the runtime, clones the installer, generates secrets, and brings the stack up. Runs once, guarded by a marker file.

reconcile mode

Verify what is already running

Skips every destructive step, reconciles containers, confirms health. Safe to run against production any time.

the guard rail we built in

Regenerating secrets would make existing data unreadable, so the role only allows it on a genuinely first run.

from manual to one click · operation

Deploying without holding the keys

Repository
The Kodus playbooks, cloned from GitLab at run time
Credentials
SSH key and token held in an encrypted store, granted per person
Inventory
The target machine, reached over the private network
Result
A verified run confirming all eight services healthy, output readable in the browser
what this changes for the team

Redeploying no longer requires the machine's location, its key, or the vault password — just an account and a button, with a log of who ran what.

05

What we learned

The problems that cost time, and what they taught us.

what we learned · six blockers

Challenges and how we overcame them

01 · silent drops
Findings generated but never posted — the publisher discarded valid suggestions on a line-mapping mismatch.
02 · migrations stuck
TypeORM wouldn't migrate an existing DB despite healthy tables and credentials — fixed with a clean reinstall.
03 · trial banner stuck
Self-hosted instance still showed a trial banner — driven by org parameters in the DB, not an env flag.
04 · services absent
Some containers never started — the vendor script doesn't always launch every service; now checked explicitly.
05 · BYOK rejected HTTP
Self-hosted endpoint failed BYOK validation — Kodus requires HTTPS as an SSRF safeguard; a TLS-terminating proxy is the clean fix.
06 · everything was public
Every service, DBs included, bound to 0.0.0.0 — fixed with nginx in front and loopback-only binding.

what we learned · skills

What we take from this

infrastructure

Multi-service systems

Eight containers with queues, two databases and a vector store, started reliably in the right order.

automation

Ansible that holds up

Roles, encrypted secrets, idempotency, and destructive steps written so they can't run twice by accident.

integration

Connecting real systems

Tokens, scopes, webhooks and callbacks between a self-hosted platform and a self-hosted Git service.

ai in practice

Running our own model

Serving an open-weights model behind a compatible API, and knowing where its limits show up.

diagnosis

Reading the failure

Container logs, service health, queues and configuration, and knowing which one a symptom points at.

working

Writing it down

Every blocker we hit became a documented fix — worth more to the next team than the deployment itself.

what we learned · what comes next

Future improvements

Add a certificate, not just nginx. Traffic is now consolidated behind one entry point, but it's still plain HTTP. A domain and TLS should come before wider use
Back up the databases. Review history and the learned standards accumulate value over time, and neither is currently protected
Watch the model under real load. Our testing volume was modest. Response time on a busy day is the number to measure next
Decide on the model trade-off. Cloud quality versus self-hosted privacy is an open call for the team, not something we could resolve in this scope
Turn on review across more repositories. The setup is per repository, and extending it is configuration rather than new work
Build the team's review rules. The feedback loop already captures accepted and rejected suggestions. Curating that into house standards is where the tool gets sharper
